# Skill: Post product to DBA

Tools: Read and Write on `products.json`; Bash to run `scripts/post_dba.js`; AskUserQuestion for missing fields, the postal code, and the pre-post confirmation.

## How this works

Confirmed by capturing real network traffic (Playwright's request/response recorder) through an actual DBA posting flow (2026-08-27, item id 24370806). DBA's "create listing" UI is a thin client over a stable JSON API — the script talks to that API directly instead of clicking through form fields, which is far more reliable than DOM selectors:

- `GET /recommerce/create/api/user/postalcode` — account default postal code.
- Navigating to `/create-item/start` shows a two-way choice screen — **Markedspladsen** (regular marketplace items) vs **Motor** (vehicles) — and only clicking "Markedspladsen" mints a new item id and redirects to `/recommerce/create/{itemId}`. This script only ever posts regular items, so it always clicks Markedspladsen; there is no vehicle-listing support. This is the only step the script drives via the browser UI rather than the API, since the item id doesn't exist until this click happens.
- `PUT /recommerce/create/api/item/{itemId}/validate` with `{"trade_type":"SELL"}` — creates the draft.
- An initial `PUT /recommerce/create/api/item/{itemId}` draft save (`commit:false`, `{trade_type, address}` when a postal code is available) happens before the first image upload — calling the image endpoint straight after `validate` with no draft save in between returned HTTP 500 in the original capture's sequence.
- **Image upload is driven through DBA's own `input[type="file"]` element (`setInputFiles`), not called as a direct API request.** Both a standalone Playwright `request` call and an in-page `fetch()` carrying identical bytes/headers/cookies got the same unexplained, bodyless HTTP 500 from `POST /recommerce/create/api/image/{itemId}` across multiple retries — ruling out a missing-header theory, since the in-page fetch should be indistinguishable from a real browser request. Something about server-side item state at that point must differ from a real user's flow in a way that was never identified. Driving the actual file input sidesteps the mystery by doing exactly what a human does; the script still observes the resulting `POST /recommerce/create/api/image/{itemId}` request via `page.waitForResponse` to read back the same `{uri, width, height}` response shape the original capture showed, rather than trusting DBA's frontend to expose it any other way. **If image upload ever needs revisiting, don't retry the direct-API approaches — they're a dead end that was tested twice.**
- `POST /recommerce/create/api/predictions/categories/{itemId}` — DBA's own AI category suggestion based on the item, keyed off title **and image**. It returns no suggestion at all if the item has no uploaded photo yet (confirmed by testing) — so the script uploads photos before calling this. DBA does not expose an API to list the Hovedkategori/Underkategori/Produktkategori dropdown tree — it's baked into DBA's frontend bundle, not fetched over the network, and cascading through it by trial and error (PUTting candidate category ids and reading back `violations`) confirmed there's no shortcut. Replicating that tree in the overlay would mean reverse-engineering and maintaining a copy of DBA's full taxonomy, which would silently go stale. So the script always uses this prediction when DBA returns one (same classifier a human would otherwise approximate by eye) and only falls back to asking the user to pick a category by hand, directly in DBA's real form, when there's no suggestion at all.
- **Title/description/price/postal code are filled through DBA's own form fields (`Annonceoverskrift`/`Beskrivelse`/`Pris`/`Postnummer` labels), not a direct API draft-save call.** A `PUT .../item/{itemId}` draft-save with `commit:false` and the full accumulated field set worked in the very first capture, but after switching image upload to the real file input (see above), that same draft-save call started returning an unexplained HTTP 400 with an empty body. The leading theory: DBA's own frontend JS persists its own draft revision immediately after a real browser-driven upload, and a blind overwrite from a separate client (Playwright's standalone `request`) conflicts with that state. Filling the rest of the form the same way a human would sidesteps this the same way the image-upload fix did.
- **Publishing happens entirely in DBA's own UI, not via an API `commit:true` call.** The script fills everything it can, then shows a review panel asking the user to click DBA's real **"Se forhåndsvisning"** button (`<button type="button">Se forhåndsvisning</button>`, no other stable selector) and complete publishing themselves from whatever DBA's preview/submit flow looks like — the script does not know that flow's shape and doesn't attempt to click through it blind. Success is detected by polling `GET /my-items/details/{itemId}/api/single?adId={itemId}` until the item's `state.type` leaves `"DRAFT"` (the original capture showed a real publish transitioning to `"PENDING"` — "Under gennemgang" — which is expected, not a failure).
- `POST /recommerce/delivery/api/delivery?finnkode={itemId}` with `{"meetup": true, "shipping": false}` — shipping method used in the original capture; **the current script does not call this** since publishing moved to DBA's own UI, so shipping method is now whatever the user picks (or DBA defaults to) during that manual flow. See Known gaps.

Dimensions (Højde/Bredde/Dybde) and condition (Stand) are always confirmed by the user through an in-page overlay before continuing — DBA's condition ids are opaque and category-specific, so the panel is never skipped even when a value is already known. But the panel arrives pre-filled rather than blank, in priority order:
1. `metadata.dimensions_cm` / `metadata.condition` on the product in `products.json`, if `add-product` predicted them from the description — pass these to the script (see Workflow) so it doesn't have to re-derive them.
2. Otherwise, the script regex-parses common size patterns out of the product's own `title`/`description` text (e.g. "180 x 90 cm" as a width×depth footprint, "62-128 cm" as an adjustable-height range, taken as its max).
3. Otherwise, the inputs are left blank for the user to fill in.
Condition defaults to id 3 ("God, brugt stand") when nothing else is known. Category is auto-accepted from DBA's own AI suggestion when available, or picked manually in DBA's real form otherwise (see above).

All user interaction happens through a floating panel injected into the DBA page itself, not terminal prompts. A terminal `readline` prompt run through an agent's sandboxed shell can end up with keystrokes that never reach the background process's stdin, leaving it stuck waiting with no visible symptom — the in-page overlay sidesteps that class of bug entirely, since every input is a click or a browser form field the user is already looking at.

## Single-item design

`scripts/post_dba.js` creates exactly one DBA item and fills it progressively (`createAndPublishListing`) — there is no separate throwaway "discovery" item. **An earlier version tried a two-item design** (a scratch item to find out what DBA wants, deleted afterward, then a second fresh item for the real listing) but hit a wall: DBA's `/create-item/start` flow turned out to always resume the *same one in-progress draft per session* rather than minting a genuinely new item id on a second navigation. Deleting the scratch item before starting the "real" one caused the second `startNewDraft()` call to land right back on that same (just-deleted) id, which then failed the real draft save with HTTP 400 — a bug that took several iterations to trace back to this root cause rather than the request-shape issues it initially looked like. **Do not reintroduce a second item/scratch-draft design** — fill one item from the start, matching how a human uses DBA's own form anyway (one draft, filled in over several steps).

The flow: create the item → upload photos through DBA's real file input (must happen before asking for a category — DBA's classifier has nothing to look at otherwise) → ask DBA for a category suggestion (or let the user pick one by hand in DBA's real form if there's no suggestion) → collect height/width/depth/condition via an overlay panel (dimensions pre-filled by guessing from the product's own `title`/`description` text) → fill title/description/price/postal code into DBA's real form fields → show a review panel telling the user to click DBA's own "Se forhåndsvisning" button and publish themselves → poll DBA's item-status endpoint until the item leaves draft state.

**Two separate parts of this flow were originally API-driven and both had to move to being UI-driven after the fact** (image upload, then title/description/price/postal code + publish) because a direct API call that worked in the original capture started failing once other parts of the item's state came from real browser interaction. See the "How this works" bullets above for the specifics. If any *other* part of this script starts failing with an unexplained error after being changed, suspect the same class of problem — a direct API call racing or conflicting with DBA's own frontend JS — before assuming the request shape itself is wrong.

The discovered fields (`{categoryId, categoryLabel, height, width, depth, condition}`) are printed as a `FIELDS <json>` line on stdout as soon as they're known — before the draft-save/publish steps that can still fail — see Workflow step 8 for how the skill persists this into `products.json` as `channels.dba.fields`.

## Known gaps

- Shipping method, listing tier/boost, and any post-preview steps (payment/checkout screens, etc.) are entirely in the user's hands now that publishing happens in DBA's own UI — the script has no opinion on them. This is a behavior change from the original API-driven design, which hardcoded meetup-only shipping and skipped the tier-selection call; now whatever the user picks (or DBA defaults to) during their manual review is what gets published.
- `furniture_brand` and other category-specific attributes beyond dimensions/condition are not collected; DBA's attribute-prediction endpoint exists (`POST /recommerce/create/api/predictions/attributes/{itemId}`) but the script does not currently call it or prompt for extra attributes.
- `waitForPublished()` polls for up to 5 minutes after the user acknowledges the review panel; if DBA's own publish flow takes longer than that (e.g. the user gets distracted mid-flow), the script times out with an error even though the user may still complete publishing afterward — worth a manual `products.json` check in that case rather than assuming it failed.

## Workflow

1. Read `products.json`. Select the requested product(s), or every product with lifecycle `status: "new"` and `channels.dba.status` not `posted` when the user says "all new products". Never post a `sold` product.
2. Validate the product has a non-empty `title`, non-empty `description`, a non-negative numeric `price`, and at least one image path that exists on disk. Ask the user for anything missing instead of guessing.
3. Confirm `DBA_SELLER_POSTAL_CODE` is set in `.env` (see `.env.example`). If missing, ask the user for the postal code and write it to `.env` before continuing. Never put it in `products.json`.
4. Show the exact listing payload (title, description, price, postal code, image paths) for one product and ask the user to confirm before doing anything external.
5. On confirmation, run:
   ```
   node scripts/post_dba.js '<product-json>'
   ```
   passing `{ "title", "description", "price", "images" }` for that product, plus `"metadata"` verbatim if the product has one (`{ "dimensions_cm": {...}, "condition": "..." }` — see `add-product`'s Metadata section for the shape), as the JSON argument. This opens a real, visible browser window (needed for login cookies; API calls run through that authenticated session).
6. The script pauses via in-page overlay panels; publishing itself is never something the script submits — it always happens in DBA's own UI, by the user's own click. Every panel states what already happened and what happens next; between panels, a brief non-interactive status line ("Starting a new listing draft…", "Uploading N photo(s)…", "Asking DBA to suggest a category…", "Filling in title, description, price, and postal code…", "Waiting for DBA to confirm the listing is published…") fills the gap instead of the panel going quiet.
   - First panel: the user logs in to DBA by hand in the browser (or resumes an existing session), then clicks "I'm logged in, continue" — the agent never sees or handles DBA credentials.
   - The script clicks "Markedspladsen" on DBA's start screen, creates the one real listing item, and uploads photos through DBA's own file input. It then asks DBA for a category suggestion. If DBA suggests one, it's used automatically (shown, not asked for). If not, a panel tells the user to pick a category directly in DBA's own form; the script polls until a valid category is saved. Either way, a panel then collects height/width/depth (cm, pre-filled by guessing from the product's own text) and a condition dropdown (defaulted); the user confirms or corrects these and clicks Continue.
   - The script fills title/description/price/postal code into DBA's real form fields, then shows a review panel with everything filled (title, price, postal code, category, dimensions, condition, image count) and a single "I've published it" button. The user must check everything in the browser, click DBA's own "Se forhåndsvisning" button themselves, and complete publishing entirely in DBA's UI — the script has no visibility into or control over that flow. Clicking "I've published it" only tells the script to start checking whether it actually happened (next step); it is not what triggers the publish.
7. Treat the run as successful only when the script prints `POSTED <listing_url>` on stdout — which only happens after `waitForPublished()` confirms via `GET /my-items/details/{itemId}/api/single?adId={itemId}` that the item's state left `DRAFT`. Any other output (`ERROR ...`, a crash, the user closing the window early, or the 5-minute polling timeout) is a failure — do not update `channels.dba.status`/`posted_at`/`listing_url` as posted in that case. A polling timeout specifically does not mean the listing wasn't published — see Known gaps.
8. Regardless of success or failure, if the script printed a `FIELDS <json>` line (the discovered `{categoryId, categoryLabel, height, width, depth, condition}`, printed as soon as those fields are known — before the draft-save/publish steps that can still fail), store it verbatim as `channels.dba.fields` on that product and update `updated_at`. This is reusable information even if the later publish step failed — persist it so a retry (or a future edit-and-repost) doesn't have to re-derive it from scratch. Read `products.json` fresh right before this write in case other state changed concurrently.
9. On success (in addition to the `FIELDS` write above), also update `channels.dba.status` to `posted`, set `channels.dba.posted_at` to the current ISO-8601 UTC time, store `channels.dba.listing_url` from the script output, set the product lifecycle `status` to `posted` if it was `new`, and append a `posted` event with channel `dba` and the `price` the listing was posted at.
10. On failure, leave `channels.dba.status`/`posted_at`/`listing_url` as they were (only `fields`, if present, and `updated_at` change), append a `post_failed` event for channel `dba` with a safe summary of the error, and report the failure to the user without claiming a post happened.
11. Write the updated `products.json` after every run — success or failure — so the `fields` sync in step 8 always lands. When posting "all new products", repeat steps 4-10 for each product one at a time — never batch multiple listings into one confirmation.

## Setup this skill depends on

- `scripts/post_dba.js` launches Chromium headed via Playwright. It uses DBA's recommerce JSON API for the steps that proved reliable (item creation, category prediction) and drives DBA's real form/buttons directly for the steps that didn't (image upload, title/description/price/postal code, and publishing itself) — see "How this works" above for why each one moved. It collects category/dimensions/condition via an in-page overlay and never submits DBA's publish action on the user's behalf — that always happens by the user's own click, in DBA's own UI.
- `DBA_SELLER_POSTAL_CODE` lives only in `.env` (gitignored), never in `products.json` or chat-derived files. `.env.example` documents the key.
- Never record or store login credentials or one-time passcodes anywhere in the repo, skill docs, or scripts. Login always happens by hand during the first pause. When capturing network traffic to debug this flow, scrub any captured login/OTP data before it's referenced anywhere persistent.
- If a run ever appears to hang with no terminal output changing, check the browser window first — the script is very likely waiting on one of the in-page overlay panels (login, category/dimensions, or publish confirmation), not stuck in the terminal.
